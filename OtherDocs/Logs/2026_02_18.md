# Development Log — Native Location Geocoding

### Date

18 February 2026

### Objective

To automatically populate geographic coordinate fields (`latitude`, `longitude`) within the speaker metadata dataset using existing `native_city` and `native_county` columns.

---

### Problem Identified

The dataset contained structured textual metadata for speaker origin:

* `native_city`
* `native_county`

However, no geographic coordinate data was present.
This prevented:

* Marker placement on Leaflet maps
* Spatial visualisation of model predictions
* Geospatial clustering or analysis

Manual entry of coordinates was deemed:

* Error-prone
* Non-reproducible
* Infeasible at scale

---

### Technical Approach

An automated geocoding pipeline was implemented using:

* Python
* `pandas`
* `geopy`
* OpenStreetMap Nominatim API

The process:

1. Combine `native_city` and `native_county`
2. Append “Ireland” to constrain search domain
3. Submit structured query to Nominatim
4. Extract latitude and longitude
5. Cache duplicate lookups
6. Write enriched dataset to new CSV

---

### Key Implementation Decisions

| Decision                  | Rationale                           |
| ------------------------- | ----------------------------------- |
| Use Nominatim             | Free, open-source, reproducible     |
| Apply 1-second rate limit | Compliance with API usage policy    |
| Cache results             | Prevent redundant API calls         |
| Create new CSV output     | Preserve original dataset integrity |

---

### Data Processing Logic

For each row:

```
native_city + ", " + native_county + ", Ireland"
```

Example:

```
"Cork, Cork, Ireland"
```

Returned:

```
51.8979, -8.4706
```

Two new columns were appended:

* `latitude`
* `longitude`

---

### Limitations Identified

* Ambiguous town names may produce inaccurate centroids
* City-level resolution may not represent precise birthplace
* Some rural locations may fail geocoding

Mitigation strategy:

* Fallback to constituency centroid (for TDs)
* Manual validation of failed geocodes
* Future integration with official Irish geospatial datasets

---

### Outcome

The enriched dataset now supports:

* Marker placement on interactive maps
* Spatial accuracy evaluation
* Visual comparison between predicted and native province

This significantly strengthens the geospatial component of the system.

# 3️⃣ Development Log — Province Boundary Optimisation

### Objective

To prepare a lightweight, production-ready province boundary dataset suitable for real-time rendering in the front-end Leaflet map.

---

### Problem Identified

A downloaded province GeoJSON file (~22MB) caused:

* System lag when opened in a text editor
* Potential front-end rendering performance issues
* Excessive geometry precision beyond application requirements

The file contained highly detailed coastline and boundary coordinates, far exceeding what was required for:

* Province-level highlighting
* Marker association
* Visual user feedback

---

### Technical Decision

It was determined that:

* High-resolution coastline data is unnecessary for a web prototype
* Simplified geometry would dramatically improve performance
* Only four polygon features (one per province) are required

---

### Processing Workflow (QGIS)

1. Loaded GeoJSON into QGIS.
2. Verified administrative boundary type.
3. Dissolved underlying administrative units (if necessary) into four province polygons.
4. Applied geometry simplification using the Douglas–Peucker algorithm.
5. Exported simplified layer as a new GeoJSON file.
6. Ensured CRS was set to **EPSG:4326 (WGS84)** for Leaflet compatibility.

---

### Key Design Rationale

| Decision               | Justification                           |
| ---------------------- | --------------------------------------- |
| Dissolve to 4 polygons | Reduce feature complexity               |
| Simplify geometry      | Improve front-end rendering performance |
| Use EPSG:4326          | Required for web mapping libraries      |
| Avoid manual editing   | Preserve reproducibility                |

---

### Outcome

The resulting file:

* Reduced dramatically in size
* Contained only four province features
* Rendered efficiently in Leaflet
* Maintained sufficient geographic accuracy

This significantly improves:

* Front-end responsiveness
* User experience
* System scalability

# 4️⃣ Development Log — Province Centroid Generation

### Objective

To generate accurate province centroid coordinates for:

* Marker placement fallback
* Province highlight focus behaviour
* Spatial prediction mapping

---

### Methodology

Province centroids were computed from simplified province polygons.

Important methodological decision:

Centroids were computed in projected CRS:

```
EPSG:2157 (Irish Transverse Mercator)
```

This avoids distortion that occurs when calculating centroids directly in geographic CRS (EPSG:4326).

After centroid computation:

* Geometry reprojected back to EPSG:4326
* X coordinate extracted as longitude
* Y coordinate extracted as latitude

---

### Technical Clarification

Coordinate system interpretation:

| Axis | Meaning   |
| ---- | --------- |
| X    | Longitude |
| Y    | Latitude  |

This prevents common coordinate inversion errors in Leaflet integration.

---

### Output

Generated dataset:

```
province_centroids.csv
```

With fields:

* province
* latitude
* longitude

These centroids are now integrated into the front-end as fallback spatial anchors.

# 5️⃣ Development Log — Coordinate Validation Pipeline

### Objective

To verify that all geocoded speaker coordinates fall within Ireland’s geographic extent.

---

### Problem Identified

Automated geocoding using OpenStreetMap may:

* Match same-named towns outside Ireland
* Return ambiguous results
* Produce incorrect spatial points

Unvalidated coordinates risk:

* Incorrect marker placement
* Invalid model evaluation
* Spatial distortion in visualisations

---

### Validation Strategy Implemented

Two-stage validation approach:

### Stage 1 — Bounding Box Validation

Coordinates validated against Ireland bounding limits:

* Latitude: 51.0 → 55.6
* Longitude: -11.2 → -5.3

Rows outside these limits were flagged and exported for review.

---

### Stage 2 (Planned) — Polygon Containment Validation

Future improvement:

* Validate coordinates using point-in-polygon check against province boundary union
* Use GeoPandas and Shapely for containment testing
* Flag spatial outliers automatically

---

### Design Justification

Bounding box validation was chosen as:

* Computationally efficient
* Sufficient for early-stage prototype validation
* Easy to document and reproduce

---

### Outcome

The coordinate dataset now supports:

* Spatial integrity assurance
* Automatic anomaly detection
* Cleaner front-end marker rendering
