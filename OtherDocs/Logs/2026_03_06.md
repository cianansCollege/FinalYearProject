2. Designing a Plug-and-Play ML Architecture

A modular system design was proposed to allow different machine learning models to be tested without changing the frontend code.

The core principle was to separate the frontend interface from the backend model logic.

Key Concept

The frontend should communicate with the backend through a stable API contract, while the backend loads whichever model plugin is selected.

This allows models to be swapped without modifying:
	•	frontend code
	•	map logic
	•	prediction display logic

⸻

3. API Contract Design

Two backend endpoints were defined.

GET /api/models

Returns the list of available models so the frontend can populate a dropdown.

Example response:

{
  "models": [
    {
      "id": "mfcc_svm_v1",
      "name": "MFCC + SVM (v1)",
      "description": "Baseline SVM model"
    }
  ]
}

POST /api/predict

Receives:
	•	recorded audio
	•	selected model_id

Returns prediction results including:
	•	predicted label
	•	confidence score
	•	class probabilities

Example structure:

{
  "request_id": "abc123",
  "model_id": "mfcc_svm_v1",
  "label": "Leinster",
  "confidence": 0.62,
  "probs": [
    {"label": "Leinster", "p": 0.62},
    {"label": "Munster", "p": 0.21}
  ]
}

This response structure allows the frontend to remain model-agnostic.

4. Backend Model Registry Concept

A model registry was introduced.

Purpose:
	•	Maintain a catalogue of available models.
	•	Allow models to be referenced using model_id.

Instead of hardcoding models with conditional logic, the backend retrieves models from the registry.

Benefits:
	•	easier model experimentation
	•	cleaner backend structure
	•	easier extension for future models

⸻

5. Model Plugin Structure

Each model should exist as a separate plugin file containing:

Required elements
	•	id
	•	name
	•	description
	•	predict() method

The predict() method performs the full inference pipeline:
	1.	Receive uploaded audio
	2.	Decode waveform
	3.	Apply preprocessing
	4.	Extract features
	5.	Run classifier
	6.	Format output into the standard API structure

⸻

6. FastAPI Backend Workflow

The FastAPI backend acts as a thin layer between the frontend and the ML models.

Prediction Flow
	1.	Frontend records user audio.
	2.	Audio and selected model_id are sent to /api/predict.
	3.	Backend validates the model ID.
	4.	Backend retrieves the model plugin from the registry.
	5.	Plugin executes predict().
	6.	Backend returns prediction results as JSON.

Models should be loaded once at server startup rather than during every prediction request.

7. Frontend Model Selection

A dropdown was added to allow users to choose between models.

Frontend behaviour:
	1.	Page loads.
	2.	Frontend calls /api/models.
	3.	Dropdown is populated with available models.
	4.	Selected model ID is stored in application state.
	5.	Prediction requests include the selected model.

This enables runtime model switching.

⸻

8. Frontend Prediction Request Flow

The frontend sends prediction requests using FormData.

Data included in the request:
	•	recorded audio blob
	•	selected model_id

Prediction flow:
	1.	User records speech.
	2.	Recording produces an audioBlob.
	3.	Frontend sends audioBlob + model_id to /api/predict.
	4.	Backend returns prediction JSON.

A dedicated api.js helper module was introduced to handle network requests.

9. Prediction Display and Map Integration

After receiving prediction results, the frontend performs two independent updates.

Prediction Panel

Displays:
	•	model used
	•	predicted province
	•	confidence score
	•	probability distribution

Handled in predictions.js.

Map Highlighting

The predicted province label is passed to the map module.

The map then:
	1.	Clears previous highlight.
	2.	Finds the corresponding province polygon.
	3.	Applies highlight styling.

Handled in map.js.

This maintains separation of concerns between:
	•	data display
	•	geographic visualization.

12. Efficient Handling of the Mozilla Common Voice Dataset

Strategies were discussed to avoid extracting the entire dataset.

Extract Metadata Only

unzip common_voice_en.zip "*.tsv"

This extracts only metadata files such as:
	•	train.tsv
	•	dev.tsv
	•	test.tsv

These files are much smaller than the audio dataset.

⸻

Extract Only Required Clips

Each metadata row contains the path to the audio clip.

A smaller dataset can be created by:
	1.	Selecting a subset of rows.
	2.	Extracting only the referenced clips.

Example subset:
	•	2000–5000 audio clips

Estimated size:
	•	~2–4GB instead of 100GB+.
